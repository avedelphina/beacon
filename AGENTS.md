# Beacon

Central console for managing a fleet of [Hermes](https://github.com/NousResearch/hermes-agent)
agents spread across hosts, profiles, and OS users — deploy, track, configure,
troubleshoot, reconcile, and decommission them from one FastAPI app instead of
an SSH session per host. Agent-type-agnostic by design: Hermes is the first
driver behind a small module interface, not the only supported type.

The authoritative documentation is [README.md](README.md) (architecture, data
model, API reference) and [ROADMAP.md](ROADMAP.md). [CHANGELOG.md](CHANGELOG.md)
follows Keep a Changelog; update it when changing behavior.

## Tech stack

- **Backend**: Python + FastAPI (`backend/`), served by uvicorn on port 8642.
  Python 3.12 in Docker (lock files were compiled with pip-compile on 3.11).
  Key deps: `fastapi`, `uvicorn[standard]`, `pyyaml`, `httpx`, `pyjwt[crypto]`,
  `itsdangerous`, `mcp` (for the board's MCP endpoint). No `pyproject.toml`;
  dependencies live in `requirements.txt`.
- **Source of truth**: the fleet (hosts, agents, templates, cron jobs, the
  access policy) lives in the SQLite store `state/beacon.db`, with a history of
  every change (`fleet_history`). YAML under `fleet/` is only the import/export
  form (`python -m backend.fleet import|export`); a store with no fleet imports
  `fleet/` once on its first start. Real inventory files are gitignored; only
  `hosts.yaml.example` is committed.
- **Frontend**: `frontend/` — a single static page, vanilla HTML/CSS/JS, no
  build step, no framework.
- **Transport**: the system `ssh` binary (`backend/ssh.py` is the only place
  that shells out) — never a Python SSH library. Static key with strict
  known-hosts checking, or an `ssh_config` file generated by a Teleport tbot
  identity (`ssh.key` and `ssh.config_file` are mutually exclusive).
- **MCP server**: `mcp/server.py` — a separate service (port 8643,
  streamable-http, endpoint `/mcp`) that exposes the fleet over MCP as a thin
  client of Beacon's own HTTP API. It has its own `mcp/requirements.txt`.
- **tbot**: `tbot/` — Teleport Machine ID sidecar (Dockerfile + `run.sh`) that
  renews SSH certificates into `tbot/data/`. Its data/storage dirs are private
  key material and are gitignored.

## Code organization

```
backend/
  app.py          FastAPI routes; confirm-gate and tier enforcement
  auth.py         Zitadel OIDC login (authorization code + PKCE) + auth/CSRF middleware
  store.py        the fleet in the operational store: records + change history
  fleet.py        YAML import/export, first-start import, `python -m backend.fleet`
  cron_store.py   cron job records
  scheduler.py    CLI cron dispatcher — no background scheduler in the app
  schemas.py      pydantic models: Host, Agent, CronJob, SSHConfig
  templates.py    config template load/validate/deep-merge under `desired`
  tiers.py        capability -> T0–T5 autonomy tier registry
  bus.py          agent bus: one A2A v1.0 SendMessage to an agent's reach.endpoint
  policy.py       the access policy (YAML text in the store): tag rules
                  (Tailscale-style) behind may_call; preview/save for the Policy
                  tab (T4, history in fleet_history)
  mailbox.py      relay + voicemail behind POST /a2a/{agent}; delivers on the
                  recipient's /mesh pull (no scheduler); slow answers come back
                  by A2A push to /a2a/{agent}/push/{id} (long work)
  opstore.py      operational store: SQLite at state/beacon.db (runtime state and
                  the fleet itself; schema and migrations live here)
  skills/         skills Beacon hands every agent via the mesh config; the host
                  sync installs them (mesh.skills, hermes_mesh_sync.install_skills)
  board.py        fleet board: cards + history in the opstore; assignment
                  notices go through the mailbox
  board_mcp.py    /board/mcp: board-only MCP tools for agents (own token) and
                  MCP clients (bearer); a fresh server per app lifespan
  mesh.py         A2A mesh: same-network peers, derived tokens, /mesh pull config,
                  `install` CLI (host bootstrap)
  ssh.py          the one place that shells out to `ssh` (run + stream_script)
  drivers/
    __init__.py   DRIVERS registry + for_agent() resolution
    hermes.py     the only driver so far: status/logs/deploy/reconcile/
                  config_diff/push_config/decommission/plugins
    hermes_mesh_sync.py  stdlib-only host-side sync, shipped by `mesh install`
    hermes_config_schema.yaml  checked-in snapshot of Hermes's DEFAULT_CONFIG,
                  used to validate config paths before push
fleet/            YAML inventory (see Tech stack)
frontend/         static page, no build
mcp/              MCP server service (own Dockerfile + requirements)
tbot/             Teleport tbot sidecar (own Dockerfile + run.sh)
scripts/dump_hermes_config_schema.py  regenerates the config-schema snapshot
tests/            pytest suite
```

A second agent type means adding a second driver module under
`backend/drivers/` and registering it in `DRIVERS` — the core should not need
to change.

## Build and run

```bash
# Local dev
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp fleet/hosts.yaml.example fleet/hosts.yaml   # first run only
.venv/bin/uvicorn backend.app:app --port 8642

# Docker (three services: tbot, beacon, mcp)
docker compose up -d --build

# Cron scheduler (external trigger, e.g. system cron / launchd, once a minute)
.venv/bin/python -m backend.scheduler tick           # dispatch due jobs
.venv/bin/python -m backend.scheduler list           # list jobs
.venv/bin/python -m backend.scheduler tick --dry-run # no host contact

# Regenerate the Hermes config-schema snapshot after a Hermes version bump
python3 scripts/dump_hermes_config_schema.py [path/to/hermes-agent]
```

## Dependency management

- `requirements.txt` / `requirements-dev.txt` / `mcp/requirements.txt` hold
  direct pins. The `*.lock` files are generated with
  `pip-compile --generate-hashes` and must be installed with
  `pip install --require-hashes -r requirements.lock` (this is what the
  Dockerfile and CI do). Regenerate the matching lock file whenever a
  requirements file changes.

## Testing

```bash
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/pytest -q
```

- `pytest.ini` sets `testpaths = tests` and `pythonpath = .` so `import
  backend` resolves without installing the package.
- `tests/conftest.py` provides the two fixtures every test relies on: `fleet`
  (points the store at a tmp dir, so tests never touch the real
  `state/beacon.db` or `fleet/`) and `fake_ssh` (replaces the `ssh` module the
  driver calls with a recorder returning canned results — no real SSH, no
  real filesystem). New driver/store tests should use these fixtures rather
  than touching real hosts or paths.
- Tests use FastAPI's `TestClient` for API tests.

## CI / deployment

- `.github/workflows/ci.yml` runs on every push/PR: `pytest -q` (after
  installing `requirements-dev.lock` and `mcp/requirements.lock` with
  `--require-hashes`), plus a `docker compose build` of all three images
  (`beacon`, `tbot`, `mcp`) in a matrix.
- Deployment is `docker compose up -d --build`. `fleet/` is bind-mounted into
  the beacon container as persistent state, not baked into the image.
  `docker-compose.yml` binds ports to 127.0.0.1 by default (`BEACON_BIND_HOST`
  overrides); only expose beyond loopback once OIDC auth is configured.
- Version is bumped in `backend/app.py` (`FastAPI(version=...)`) alongside a
  CHANGELOG entry.

## Conventions

- **Mutations are gated by autonomy tiers** (`backend/tiers.py`): every
  capability at T2+ requires `confirm=true`; without it the endpoint returns a
  `{"would_run": true, ...}` description instead of acting. T4/T5 additionally
  require a human browser session — MCP's bearer token cannot execute them.
  Register any new mutating capability in `CAPABILITY_TIERS` with a rationale.
- **Live state is never stored in the fleet records.** `status()` and
  `config_diff()` poll the host fresh; fleet records hold only intent
  (`desired`). Runtime facts (pulls, chat reports, mailbox) have their own
  tables.
- **Agent access policy is one rule**, `mesh.may_call(caller, target)`
  (the stored policy's tag rules via `backend/policy.py`, plus `reach.callers`;
  Beacon is always allowed; no policy means Beacon only). Any new path by which one
  agent reaches or hands work to another must check it, as direct calls,
  the mailbox and board assignment do.
- **The host sync only touches what Beacon created** (`managed.json` beside
  it). Never write code that replaces an agent's `a2a_agents` or caller lists
  wholesale: an agent's owner may have added their own entries.
- **Templates deep-merge** into an agent's `desired` in listed order, agent
  wins; the merge happens on read, never rewrites the file.
- **Config pushes are validated** against
  `backend/drivers/hermes_config_schema.yaml` before running `hermes config
  set`, because the Hermes CLI silently accepts unknown subkeys.
- **Code style**: modern type hints (`str | None`), pydantic models for all
  YAML records and request bodies, small modules with docstrings that explain
  *why* a decision was made rather than what the code does. Comments follow
  that same convention — keep them when editing nearby code.
- **No linter/formatter is configured** in the repo (no ruff/flake8/black
  config, none in CI); match the surrounding style.
- Frontend has no build step — edit `frontend/app.js`/`index.html`/`styles.css`
  directly.

## Security considerations

- **Never commit secrets or real inventory.** `state/` (the database, with the
  whole fleet in it) is gitignored too, and so is any exported fleet. Gitignored: `.env`,
  `fleet/hosts.yaml`, `fleet/agents/*.yaml`, `fleet/templates/*.yaml`,
  `fleet/cron_jobs/*.yaml`, `fleet/decommissioned/`, `tbot/data/`,
  `tbot/storage/`. Fleet records store `.env` key *names* only (`env_keys`) —
  secret values never leave the host. A2A tokens are derived from one
  Beacon env var, `BEACON_A2A_SECRET`, never stored in the fleet or returned by
  the API — except `GET /mesh/{agent}`, which returns only that agent's
  config and accepts only its own derived pull token (no session, no MCP
  bearer). `mesh install` output contains a token: pipe it, don't keep it.
  The install script schedules itself only when the operator passes `--schedule`
  (the enrollment command does); otherwise it prints the cron line.
- **SSH host-key checking is strict.** Static-key hosts require a reviewed
  known-hosts file (`BEACON_KNOWN_HOSTS`); Beacon fails closed and never
  trusts a new key automatically. `config_file` hosts defer to that file's
  own `Host` block.
- **Auth is opt-in but required before exposing the service.** With
  `ZITADEL_ISSUER`/`ZITADEL_CLIENT_ID` unset, every route is open. When set,
  all routes except `/auth/*` need a session (8h signed cookie, Secure by
  default) and `BEACON_ALLOWED_EMAILS` (exact email allowlist) is required.
  Browser mutations require a same-origin `Origin`/`Referer` header (CSRF
  middleware). `BEACON_MCP_TOKEN` is a static bearer accepted as an
  alternative credential, scoped to that one token.
- **The MCP server mirrors the API's confirm gate**: its mutating tools take
  `confirm: bool = False` and describe instead of act without it, on top of
  `destructiveHint` annotations — two independent gates.
- **Cron jobs execute no arbitrary shell**: only the fixed actions `restart`,
  `status`, and the workflow-gated `push_config` action are recognized. Scheduled
  `push_config` is currently fail-closed and cannot execute until scheduler-side
  workflow integration exists; the YAML record is not an approval bypass.
- Only run one tbot at a time against a given `tbot/storage` — Teleport locks
  the bot identity if two processes renew from the same stored credential.

## Known limitations (don't "fix" silently — see ROADMAP.md)

- Hermes is the only implemented driver.
- Audit trail is partial: fleet changes keep who made them (`fleet_history`); actions on hosts (deploy, push, restart) are not recorded yet.
- Pull-based only: nothing polls or alerts on its own. (The mailbox delivers
  when an agent's own sync pulls, not on a Beacon timer.)
